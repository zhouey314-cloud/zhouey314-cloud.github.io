01这是什么

接入 AI 接口之后，还需要回答：流在哪断开、请求是否到达上游、观察是否完整、故障后能否继续使用。

我把责任分开：网关负责传递 HTTP / SSE 与明确的传输状态；观察器记录允许保留的协议元数据；使用者根据报告继续排查。告警不进入模型响应，标签异常也不直接升级为真实模型身份结论。

交付与验收：本地固定路由网关、事件与报告、隔离接入和退出步骤、容量配置与恢复回归。先检查已有合成报告，再按运行命令复现流式中断、超限拒绝和名额释放；本站检查器只读取报告。

03我做了什么

我的责任覆盖协议接入、请求生命周期、可观测性与退出恢复。

接口与凭据：我实现 Responses、Chat Completions 与 Anthropic Messages 的 JSON / SSE 转发，处理两向连接级头部过滤，并分离本地认证与上游凭据。调用方可以使用隔离配置接入，而不覆盖原有订阅登录。

生命周期：我处理超时、取消、流式背压和在途容量，让请求体读取、上游调用和完整 SSE 共同占用一个名额，完成或异常结束后释放。

观察与交接：我把解析、检测和报告放在独立的有界队列中，显式记录观察丢失与真实传输终止原因；同时保留状态、容量、报告与退出恢复命令。报告只保存白名单元数据，不持久化用户提示词、回答或认证头正文。

04工程判断

01 / 容量覆盖完整请求，而不只限制建立连接

SSE 仍在输出时，请求还占用资源，因此名额保持到完整流结束。满额时，新请求在本地返回 503 与 Retry-After，不触达上游；已有流继续处理。挂起 SSE、上游计数和释放后再次请求共同验证这条边界。

02 / 业务转发与观察失败分开报告

响应字节先转发，再交给有界观察队列。观察队列拥塞可以减少证据量，但必须显示 monitoring_degraded；超时、取消等真实传输原因仍保留。这样才能区分“业务请求失败”和“监测证据不完整”。

03 / 告警描述可见现象，身份结论保留证据门槛

模型声明变化是标签不符合预期，协议错误也可能来自参数或网关。项目始终保留 identity_status=unverified；默认被动模式不追加模型请求。可选复核需要单独配置和正数请求预算，不能把请求数预算当作金额硬上限。

05验收与交接

验收一条调用链，要同时检查正常响应、失败状态和恢复后的下一次请求。

可从一个受控端点开始：明确协议、请求形态和脱敏样例，比较直连与网关的响应实体；挂起一条 SSE，确认新增超限请求未到上游，再释放连接并重新请求；另行核对观察丢失、超时和取消的报告。交接时留下接入、容量参数、报告位置与退出方式。

已有证据：公开合成演示保留原报告、来源记录与后续请求；本地测试覆盖协议实体、凭据隔离、取消、超时和容量释放。真实客户端到模拟端点的接入记录与压力记录分别注明测试环境。

这些证据证明受控环境中的传输和排查机制，未建立客户生产容量、真实中转站模型身份指纹或校准准确率。被动模式仍有开销；原生 WebSocket、完整 IDE 覆盖与生产进程监督也不在当前实现内。
